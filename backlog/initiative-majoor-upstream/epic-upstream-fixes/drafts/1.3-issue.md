**Title:** Multi-card delete and bulk rating fail partway at hard-coded rate limits; make the caps configurable

### Summary

Two write routes have fixed per-client limits:

- single-asset delete: 20 requests per 60 s (`routes/assets/route_actions_delete.py`)
- rating and tag writes: 30 requests per 60 s (`_prepare_asset_op_request` in
  `routes/handlers/assets_impl.py`, shared by `asset_rating` and `asset_tags`)

The grid sends one request per card for multi-card delete ("Delete N files") and for rating hotkeys
on a selection. Any selection larger than the cap fails partway: the first 20 (or 30) succeed and the
rest return `RATE_LIMITED`. On a trusted single-user instance there is no way to raise the cap without
editing the source.

### Reproducer (current main, 599b47df)

1. Select 25 cards in the grid.
2. Right-click, then **Delete 25 files**, then confirm.
3. 20 files are deleted. The remaining 5 fail: `GridContextMenu.ts` calls `deleteAsset` once per card,
   and requests 21–25 get `RATE_LIMITED` from the server.

The same happens with 31+ cards and a number-key rating.

### Proposal

Add two env knobs, read with the existing `_env_int` helper in `config.py`:

| Variable | Default | Range |
|---|---|---|
| `MJR_AM_DELETE_RATE_LIMIT` | 20 | 1–10000 per 60 s |
| `MJR_AM_ASSET_WRITE_RATE_LIMIT` | 30 | 1–10000 per 60 s |

Defaults stay as they are, so nothing changes unless an operator opts in. Invalid values fall back to
the default and out-of-range values clamp, both with the usual warning log. Both knobs go in the Rate
Limiting section of `docs/SECURITY_ENV_VARS.md`.

This does not replace a real bulk path. Routing multi-card delete through the existing bulk
`assets/delete` endpoint is a separate change I'd like to propose next. The knobs still help bulk
rating and tagging, and any external tool that drives the per-asset endpoints.

I have a branch with this and tests and can open a PR if you are happy with the approach.
