**Title:** Proposal: bulk tag and rating edits across a selection

### Problem

- **Tags:** "Edit tags" and the `T` key edit one card at a time. There is no way to add or remove a
  tag across a selection.
- **Ratings:** the 0–5 hotkeys do walk the selection (`ratingHotkeysController.ts`), but they send one
  `POST /mjr/am/asset/rating` per card at concurrency 5. The route allows 30 requests per minute, so
  a larger selection fails partway. Failures show as per-asset toasts, and the swallowed errors leave
  cards out of sync. The "Set rating" submenu only rates the clicked card, even when several are
  selected.

### Proposal

**Backend:** two batch routes alongside the existing single-asset ones. They reuse the same
validation, DB update and `enqueue_rating_tags_sync`, so ExifTool file sync stays in the background
queue as it is today.

```http
POST /mjr/am/assets/rating   {"ids": [..], "rating": 0-5}
POST /mjr/am/assets/tags     {"ids": [..], "add": ["tag", ..], "remove": ["tag", ..]}
```

- The tags route merges server-side, per asset: `(existing ∪ add) − remove`, under the existing
  sanitisation limits (`max_tag_length`, `max_tags_per_asset`). Other tags are never clobbered, and a
  card edited elsewhere in the meantime is not overwritten with stale client state.
- Both routes return per-asset results with partial success (`Result` pattern). The rating route
  returns `{updated_ids, failed, rating}`. The tags route returns
  `{updated_ids, unchanged_ids, failed, tags}`, where `tags` holds each asset's final tags. Both cap
  ids at 500 per request and have their own rate limit (10 per minute, like `assets/delete`).
- The new operation names are treated as rating/tags writes by the safe-mode gate, exactly like the
  single routes.
- Both emit the same per-asset update events the single-asset routes emit, so open grids and viewers update
  live.

**UI:**

- Rating hotkeys and the "Set rating" submenu, when several cards are selected, call the batch
  route in chunks.
  - The submenu label reads "Set rating (N selected)", but only when the right-clicked card is part
    of the selection. Otherwise the single-card behaviour is unchanged.
  - Badges update through the existing `mjr:asset-rating-changed` event, for confirmed ids only.
  - Rapid repeated presses are serialized, and the last one wins.
- "Edit tags (N selected)" on a multi-selection opens a small bulk editor:
  - It shows each tag's coverage, e.g. `portrait (37/100)`.
  - Adding a tag applies it to all selected cards. Removing a tag removes it from all of them.
  - Nothing is sent for tags the user did not touch.
- A progress toast appears when a selection spans more than one chunk.

### Alternative considered

Client-side pacing over the single-asset routes, for example a queue at 25 per minute with retry:
- No backend change.
- 1000 cards would take about 40 minutes.
- Read-modify-write merges in the browser can lose concurrent edits.

The batch routes avoid both problems.

Both are built and tested on branches, as two independent PRs: rating, and tags.

### Questions for you

1. Are you happy with batch routes, or would you prefer the client-pacing approach?
2. Is a separate bulk tag editor the right call, rather than giving `TagsEditor` a bulk mode? I chose
   a separate component to leave single-card editing untouched.
