**Title:** Proposal: "Empty trash" for files trashed from Majoor's folders

### Problem

Majoor deletes through `send2trash` (`features/assets/delete_service.py`). Nothing in Majoor ever
lists or clears what it trashed. On a Linux server where output sits on its own volume (Docker
volumes, NAS mounts), deleted files land in `<volume>/.Trash-<uid>/` and stay there indefinitely.
Disk usage does not drop after curation, and there is no desktop trash UI to empty, because the
machine is headless.

### Proposal

An **Empty trash…** item in the grid's empty-area menu (or Settings → Maintenance). It shows a
count and size, asks for confirmation, and then permanently removes the files Majoor sent to the
trash.

```http
GET  /mjr/am/trash          -> {"count": 123, "bytes": 4567890, "supported": true}
POST /mjr/am/trash/empty    -> {"removed": 123, "failed": [...]}
```

Scope, which needs your view:

- **Only Majoor's own roots:** never the user's whole OS trash. The backend looks at the
  freedesktop trash directories that can hold Majoor deletions: `<topdir>/.Trash-<uid>/` and
  `<topdir>/.Trash/<uid>/` for each volume holding an output, input or custom root, plus
  `~/.local/share/Trash`. It removes only the entries whose `.trashinfo` `Path=` lies inside one of
  Majoor's roots. Each removal deletes both `files/<name>` and `info/<name>.trashinfo`, with names
  handled as opaque strings, including spaces and `%`-escapes.
- **Platforms:** freedesktop (Linux/BSD) is well-defined. Windows (`$RECYCLE.BIN`) and macOS
  (`~/.Trash`) have no reliable way to tell which entries came from Majoor without shell APIs.
  Proposal: `supported: false` there, and the menu item is hidden.
- **Safety:** this is what I built.
  - The `trash_empty` operation sits on the existing delete gate (`allow_delete` /
    `MAJOOR_ALLOW_DELETE`), so emptying is off whenever deleting is. It also requires CSRF, write
    access, a rate limit and an audit entry (counts only).
  - Trash directories are used only if they are owned by the current user and are not group- or
    world-writable, following the freedesktop spec. That matters on shared or removable mounts.
  - Removal works through directory file descriptors opened with `O_NOFOLLOW`, re-checking
    ownership with `fstat` and unlinking by bare name. A directory swapped for a symlink mid-run
    cannot redirect the deletion.
  - Only files are removed. Directory payloads, orphans, malformed or crafted `.trashinfo` files,
    and entries from outside the roots are never touched.
  - The service has 100% line and branch test coverage, including security tests for the attacks
    above.
  - The GET only reports `{supported, count, bytes}` and never paths.

### Alternatives

- Expiry instead of an on-demand empty: a setting such as "remove Majoor trash older than N days".
  It could reuse the same code later. We'd start with the explicit action.
- Unlink instead of trash: a setting to bypass the trash on delete. Simpler, but it loses the
  undo window.

### Questions for you

1. Is the "only entries whose original path is inside a Majoor root" scope right, and is
   Linux-only acceptable for v1?
2. I put it in the Status panel's maintenance actions, beside Reset index. The empty-grid context
   menu only opens in folder-browsing scope. Is that the right home?
3. Selection is by original location, so files someone else's tool trashed *from Majoor's folders*
   are included. The confirm dialog and docs say so. Is that acceptable?
