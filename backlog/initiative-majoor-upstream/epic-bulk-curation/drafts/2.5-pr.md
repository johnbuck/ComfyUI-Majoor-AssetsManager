**Title:** feat: "Empty trash" for files trashed from Majoor's folders

Closes #279

The proposal and its open scope questions are in #279. I'm opening the code now so you can judge it directly; happy to change anything in it.

### What changed and why

Majoor deletes through `send2trash`, and on Linux nothing ever clears that trash. Headless servers
keep every deleted image on disk indefinitely. This adds an explicit, guarded "Empty trash" action.

**Service** (`features/assets/trash_service.py`, new, 100% line and branch coverage)

- **Supported platforms:** Linux and the BSDs only. Elsewhere the route reports
  `supported: false` and the button is hidden.
- **Trash directories:** the home trash (`$XDG_DATA_HOME/Trash`), plus each root mount's
  `.Trash-<uid>` and sticky `.Trash/<uid>`. A directory is used only if it is owned by the current
  user and not group- or world-writable, and the same applies to its `files/` and `info/`.
- **Selection:** an entry is selected only if its `.trashinfo` `Path=`, URL-decoded and resolved
  against the topdir when relative, lies inside a Majoor root. The check uses path components and
  matches both lexical and realpath forms, so roots behind symlinks still match.
- **Never selected:**
  - malformed or oversized trashinfo files;
  - entries containing NUL;
  - crafted info names (`.trashinfo`, `..trashinfo`, …);
  - orphans;
  - anything from outside the roots.
- **Removal:** descriptor-relative only. The trash dir, `files/` and `info/` are opened with
  `O_NOFOLLOW`, ownership is re-checked with `fstat`, and payload and trashinfo are unlinked by bare
  name. Only regular files and symlinks are removed; directory payloads are skipped and reported. A
  directory swapped for a symlink mid-run cannot redirect the deletion.

**Routes** (`routes/handlers/db_maintenance.py`)

- `GET /mjr/am/trash` returns `{supported, count, bytes}`, with no paths. It requires write access
  and allows 20 requests per minute.
- `POST /mjr/am/trash/empty` returns `{removed, bytes, skipped_dirs, failed}`. It requires CSRF and
  write access, allows 3 requests per minute, and writes one audit entry with counts only.
- `trash_empty` sits on the existing delete gate (`allow_delete` / `MAJOOR_ALLOW_DELETE`), so
  emptying is disabled exactly when deleting is.
- Both routes scan off the event loop.

**UI**

- An "Empty trash" button in the Status panel's maintenance actions, beside Reset index. It is
  hidden when unsupported and disabled with a tooltip when delete is off.
- The flow:
  - It fetches the count first. At 0 it shows "Trash is empty".
  - Otherwise it asks: "Permanently delete N trashed files (size) that came from Majoor's folders?
    This cannot be undone."
  - It then empties and shows a result toast.

### Security review

Two adversarial review passes ran on this branch, and their findings are fixed and tested:
- ownership checks;
- descriptor-relative removal;
- the crafted-name guard;
- NUL handling;
- the off-loop scan;
- the `O_NOFOLLOW` trashinfo read.

`tests/security/test_trash_empty.py` covers outside-root and traversal `Path=` values, symlinked
payloads and directories, a non-sticky or symlinked `.Trash`, foreign ownership, permissive modes,
and swapping `files/` or `info/` for symlinks after the scan.

### How to test

- `pytest -k trash`: unit, security and route tests, including the real delete gate.
- Vitest (`empty_trash_action.vitest.ts`): every confirm/result branch.
- Manual on Linux:
  1. Delete a few images in Majoor.
  2. Check that they appear in `.Trash-<uid>/files`.
  3. Status panel, then **Empty trash**, then confirm. They are gone, and other trash entries are
     untouched.
