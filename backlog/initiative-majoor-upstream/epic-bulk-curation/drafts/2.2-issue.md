**Title:** Multi-card delete sends one request per card instead of using the bulk `assets/delete` endpoint

### Problem

"Delete N files…" in the grid context menu (`GridContextMenu.ts`, around line 1716) and the Delete
key on a selection (`GridKeyboard.ts`, around line 801) both loop over the selection and call
`deleteAsset()` once per card. That sends one `POST /mjr/am/asset/delete` per card, and that route
is capped at 20 requests per minute. A 100-card delete removes 20 files and then fails the rest.

The bulk endpoint `POST /mjr/am/assets/delete` already exists. It uses the same send2trash path,
validates paths, returns partial results (`deleted_ids` / `failed_ids`), and has a client wrapper
(`deleteAssets(ids)` in `ui/api/clientOps.ts`). Its only caller today is the duplicates cleanup.

Related: #273 / #276 make the per-route caps configurable. That helps, but the endpoint swap is the
real fix.

### Reproducer

1. Select 30 cards.
2. Right-click, then **Delete 30 files…**, then confirm.
3. 20 files are deleted. The remaining 10 fail with `RATE_LIMITED`.

### Proposed fix

- **One bulk request per chunk.** Both multi-card paths call `deleteAssets()` with the selected ids in
  chunks of at most 500 per request. SQLite's bound-parameter limit makes larger requests unsafe, and
  the bulk route allows 10 requests per minute, which covers 5000 cards.
- **Accounting.**
  - Each chunk's `deleted_ids` removes cards from the grid.
  - Ids not confirmed as deleted count as failed in the existing summary toast.
  - A progress toast appears when there is more than one chunk.
- **A bad entry no longer sinks its batch.** The bulk route's validation is all-or-nothing: one stale
  id (already deleted elsewhere) or one out-of-root path rejects the whole batch before anything is
  deleted. The route has no way to say which entry was the problem.
  - Proposed backend change, additive only: the error carries `meta.missing_ids` for NOT_FOUND and
    `meta.rejected_ids` for a FORBIDDEN or INVALID_INPUT path.
  - The UI drops those entries and retries the rest once.
  - It falls back to one-by-one deletes only when the server names no entry.
  - A rate-limited batch is reported as failed rather than retried one by one.
- **Unchanged.**
  - Assets without an id (filepath-only browser cards) keep using the single-delete call.
  - The menu keeps its `confirmDeletion(count)` dialog. The Delete key keeps its current behaviour.
- **Fixed along the way.** `deleteAssets()` used to emit `mjr:assets-deleted` for every requested id,
  even after a partial failure. It now emits only the server's `deleted_ids`.
- **Docs.** `docs/API_REFERENCE.md` shows the request body as `{"asset_ids": [...]}`, but the handler
  reads `{"ids": [...]}`. The response example now uses the real keys.

The fix is built and tested on a branch: Vitest and pytest pass, and the quality gate is green. I can open
a PR once you've had a look.
