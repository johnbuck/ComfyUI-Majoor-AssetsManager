**Title:** Multi-card delete sends one request per card instead of using the bulk `assets/delete` endpoint

### Problem

"Delete N files…" in the grid context menu (`GridContextMenu.ts`, around line 1716) and the Delete
key on a selection (`GridKeyboard.ts`, around line 801) both loop over the selection and call
`deleteAsset()` once per card. That sends one `POST /mjr/am/asset/delete` per card, and that route
is capped at 20 requests per minute. A 100-card delete removes 20 files and then fails the rest.

The bulk endpoint `POST /mjr/am/assets/delete` already exists. It uses the same send2trash path,
validates paths, returns partial results (`deleted_ids` / `failed_ids`), and has a client wrapper
(`deleteAssets(ids)` in `ui/api/clientOps.ts`). Its only caller today is the duplicates cleanup.

Related: #273 / #276 make the per-route caps configurable. That helps, but the endpoint swap is the
real fix.

### Reproducer

1. Select 30 cards.
2. Right-click, then **Delete 30 files…**, then confirm.
3. 20 files are deleted. The remaining 10 fail with `RATE_LIMITED`.

### Proposed fix

- Both multi-card paths call `deleteAssets()` with the selected ids, in chunks of at most 500 ids per
  request. SQLite's bound-parameter limit makes larger single requests unsafe, and the bulk route
  allows 10 requests per minute, which covers 5000 cards.
- Each chunk's `deleted_ids` removes cards from the grid. `failed_ids` feed the existing error
  summary toast. A progress toast appears when there is more than one chunk.
- Assets without an id (filepath-only browser cards) keep using the single-delete call. The bulk
  endpoint takes ids only.
- The menu path keeps the existing `confirmDeletion(count)` dialog. The keyboard path keeps whatever
  confirmation behaviour it has today.
- Docs fix while there: `docs/API_REFERENCE.md` shows the request body as `{"asset_ids": [...]}`,
  but the handler reads `{"ids": [...]}`.

I have the fix planned with Vitest coverage and can open a PR once you've had a look.
