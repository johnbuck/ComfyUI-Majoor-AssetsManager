**Title:** Proposal: a small public API so other extensions can add items to Majoor's context menus

### Problem

Other ComfyUI extensions have no supported way to add an entry to Majoor's grid or viewer context
menu. The menu is a Vue node teleported to `<body>` and remounted on every open. Today an extension
has to:
- watch `contextmenu` events to learn which card was clicked;
- run a body-wide `MutationObserver` to re-append a hand-built `.mjr-context-menu-item` each time the
  menu appears;
- read the selection from `window.__MJR_LAST_SELECTION_GRID__.dataset.mjrSelectedAssetIds`.

That breaks whenever the menu markup or those internals change. Majoor already builds its menus from
plain item objects (`createItem(...)` in `ui/features/contextmenu/GridContextMenu.ts`). The builders
already hold a rich context (clicked asset, card, grid container, panel state, selection snapshot), so
a registry needs very little new machinery.

### Proposed API (minimal)

```js
// Available once Majoor's UI has loaded; also announced with a window event for late listeners.
const api = window.MajoorAssetsManager?.api ?? await new Promise((r) =>
    window.addEventListener("mjr:api-ready", (e) => r(e.detail), { once: true }));

const unregister = api.contextMenu.register({
    id: "my-ext.rate",                       // unique; re-registering replaces
    menus: ["grid-asset"],                   // "grid-asset" | "grid-empty" | "grid-folder" | "viewer"
    order: 100,                              // optional; extension items render after Majoor's own, in order
    items(ctx) {                             // called on every open; return [] to show nothing
        return [{
            label: `Rate ${ctx.selection.count} image(s)`,
            icon: "pi pi-star",
            onSelect: () => doSomething(ctx.selection.assets),
        }];
    },
});
```

- `ctx` is a frozen, documented snapshot of what the builders already have:
  - `menu`: which menu is opening;
  - `asset`: the clicked asset;
  - `selection`: `{ ids, assets, count }`;
  - `scope`: the grid's scope and subfolder (empty in the viewer).
- Assets are a flat, frozen `AssetSnapshot`: `{ id, filename, subfolder, filepath, type, kind, rating,
  tags }`. Extensions never touch Majoor's live asset objects or DOM nodes, so Majoor stays free to
  change both.
- Items support `label`, `icon`, `disabled`, `submenu` (same shape, nested), `onSelect`, and an
  optional `separatorBefore`. Majoor renders them exactly like its own items.
- An extension's group of items sits below a separator, after Majoor's items, so built-in entries
  never move.
- Isolation: an `items()` that throws or returns garbage is logged and skipped, and the menu still
  opens. `onSelect` errors are caught and shown as a toast. One extension cannot break the menu.
- `unregister()` removes the registration.

### Scope of the PR (built and tested on a branch; held until you've had a look)

- `ui/features/contextmenu/menuRegistry.ts`: the registry, item validation and the context builder.
- Wiring in the grid (asset, empty and folder builders) and viewer menus.
- `window.MajoorAssetsManager.api` plus the `mjr:api-ready` event.
- Vitest tests: registration, ordering, isolation, unregister.
- `docs/EXTENSION_API.md` with a short example extension.
- Majoor's own menus are unchanged when nothing is registered. 24 Vitest cases cover ordering,
  isolation, replace and unregister, submenus, the frozen snapshot, and the ready event.

### Questions for you

1. Would you rather expose the API through ComfyUI's own extension mechanism? For example, Majoor
   could look for a `majoorContextMenuItems` hook on extensions registered via `app.registerExtension`,
   instead of a `window` global. The global is simpler and works for non-ComfyUI scripts. The
   ComfyUI hook is more idiomatic.
2. Are the four menu ids the right granularity?
3. Should the API carry a version (`api.version = 1`) from day one?

Motivation: bulk curation tools (rating, tagging, cleanup) built as separate extensions on top of
Majoor. This is the first of a few proposals; bulk delete, bulk tag/rate and an "empty trash" action
follow separately.
